## Was stimmt

Anreisezeitpunkt zu, `STICHTAG_5`/`STICHTAG_8` sind `Date.UTC`-Werte, und die

Einzelnacht 30.06.→01.07.2026 → r32 ✓     01.07.→02.07.2026 → r50 ✓

Die Nacht vom 30.06. auf den 01.07. bleibt bei 3,2 % — richtig, weil die
Nächtigung dem Anreisetag zugeordnet wird. **Anteiliges Splitting statt Pauschalsatz

**Keine Zeitzonen- oder Off-by-one-Fehler.** Durchgehend `Date.UTC` / `getUTC*`,

        DE-Transaktionsverlauf) → alle Pflichtspalten gefunden ✓

**Fehlerbehandlung bei kaputten Zeilen — gut.** Leeres Datum, 0 Nächte, negative

## Bugs

### B1 · Drei-Monats-Grenze läuft bei Monatsenden über — Zeile 334 · **kritisch**

`setUTCMonth(+3)` kennt keine Monatsenden-Klemmung: der 31.03. + 3 Monate wird zum
31.06., und das rollt JavaScript still auf den **01.07.** weiter. Die Frist wird
dadurch ein bis zwei Tage zu spät angesetzt.

```js
// index.html:334
const limit=new Date(a); limit.setUTCMonth(limit.getUTCMonth()+3);
const exempt = b > limit.getTime();
```

Reproduktion:

```
01.01.2026 → 02.04.2026    91 N   exempt=true    ✓ erwartet
31.03.2026 → 01.07.2026    92 N   exempt=false   ✗ 3 Monate ab 31.03. enden mit
                                                   Ablauf des 30.06. (§ 902 ABGB)
30.11.2026 → 01.03.2027     91 N   exempt=false  ✗ Frist endet 28.02.2027,
                                                   Code rechnet 02.03.2027
```

Ein Aufenthalt mit **mehr** Nächten wird also nicht befreit, ein kürzerer schon —
allein wegen des Anreisetags. Betroffen sind Anreisen am 29./30./31., wenn der
Zielmonat kürzer ist.

### B2 · Befreiung erfasst den ganzen Aufenthalt statt nur die Nächte jenseits der Frist — Zeilen 335, 339–340 · **kritisch, rechtlich zu klären**

Ist `exempt` gesetzt, werden **alle** Nächte mit 0 gerechnet, auch die ersten
drei Monate:

```js
// index.html:339-340
const base = exempt ? 0 : per/(ustF+e);
const tax  = exempt ? 0 : base*e;
```

Das erzeugt eine Klippe, die für sich schon verdächtig ist:

```
01.01.–01.04.2026   90 Nächte, 10.000 €  →  276,91 € Ortstaxe
01.01.–05.04.2026   94 Nächte, 10.000 €  →    0,00 € Ortstaxe
```

Vier Nächte mehr, 277 € weniger Abgabe. Nach R5 bleiben die ersten drei Monate
abgabepflichtig, befreit sind nur die Nächte danach. Wäre das richtig, würde das
Tool bei jedem Langzeitgast **zu wenig** ausweisen — der teure Fehler, weil
Nachforderungen und Säumniszuschläge drohen.

⚠️ **Vor der Umsetzung mit der MA 6 abklären** (`kanzlei-arl@ma06.wien.gv.at`,
+43 1 4000-86380). Meine Quellen sind Sekundärliteratur, nicht der Gesetzestext.

### B3 · Negative Beträge werden still gegengerechnet — Zeilen 320, 332 · **wichtig**

`parseMoney` liefert für `-200,00` korrekt `-200`, die Prüfung `if(!amt)` (Z. 332)
fängt aber nur die 0 ab.

```
Buchung P  +200,00 €  →  +9,52 €
Buchung M  -200,00 €  →  -9,52 €
Monatssumme: 0,00 €      Warnungen: KEINE
```

Eine Rückerstattungs- oder Anpassungszeile kann die Monatsmeldung damit
unbemerkt auf null ziehen. Besonders relevant, weil `findCol` auch den
Transaktionsverlauf-Export akzeptiert (über `Bruttoeinkünfte`), und der enthält
solche Zeilen regelmäßig.

### B4 · Statusfilter erkennt nur Stornos — Zeile 322 · **wichtig**

`/storn|cancel/i` lässt alles andere durch:

```
Storniert  → übersprungen ✓      Ausstehend  → GEZÄHLT ✗
Canceled   → übersprungen ✓      Anfrage     → GEZÄHLT ✗
Bestätigt  → gezählt ✓           Pending     → GEZÄHLT ✗
                                 Abgelaufen  → GEZÄHLT ✗
```

Anfragen und abgelaufene Buchungen sind nie stattgefundene Nächtigungen. Hier
wird **zu viel** gemeldet.

### B5 · Summenzeile weicht von der Summe der angezeigten Zeilen ab — Zeilen 431–438, 454 · **wichtig**

Die Monatszeilen zeigen `Math.round(m.tax*100)/100`, die Summenzeile rundet
dagegen den **ungerundeten** Gesamtwert:

```
Drei Monate zu je 100,00 €:   Zeilen ergeben 14,28 €, Summenzeile zeigt 14,29 €
Drei Monate zu je 102,00 €:   Zeilen ergeben 14,58 €, Summenzeile zeigt 14,57 €
```

Überwiesen wird pro Monat der gerundete Betrag — die Summenzeile beschreibt also
einen Betrag, den nie jemand zahlt. Im PDF, das an die MA 6 geht, ist das eine
Zahl, die man erklären muss. Gleiches Muster in der Überweisungstabelle (Z. 454)
und im CSV-Export (Z. 489).

### B6 · `Math.round(x*100)/100` rundet gleitkommabedingt falsch — Zeilen 436, 438, 451, 454, 471, 489, 494 · **wichtig**

```
Math.round(1.005*100)/100 = 1.00   (kaufmännisch: 1,01)
Math.round(8.165*100)/100 = 8.16   (kaufmännisch: 8,17)
Math.round(1.015*100)/100 = 1.01   (kaufmännisch: 1,02)
```

`1.005*100` ist binär `100.49999999999999`. Der Text unter „Wie gerechnet wird"
verspricht kaufmännische Rundung — in diesen Fällen wird abgeschnitten. Ein Cent,
aber systematisch zulasten der Abgabe.

### B7 · Kurz-PDF blendet die Warnhinweise aus — Zeile 114 · **wichtig**

```css
body.print-months #rows-wrap, body.print-months #rows-h, body.print-months #warnings,
```

Genau das Dokument, das man weitergibt, verschweigt „3 Buchungen übersprungen —
Datum nicht lesbar". Der Empfänger sieht eine vollständig wirkende Monatsübersicht,
die es nicht ist. Die Detailtabelle auszublenden ist richtig, die Warnungen nicht.

### B8 · Gastnamen und Codes gehen ungeprüft in `innerHTML` — Zeilen 328–332, 465–478 · **wichtig**

```
Gastname "<img src=x onerror=alert(1)>" → landet unescaped in der Tabelle
```

Das Tool verarbeitet die eigene CSV, ein Angreifer ist also nicht das
Hauptszenario — aber ein Name mit `<` oder `&` zerlegt die Tabelle sichtbar, und
die Seite läuft öffentlich unter `manuel.tools`. Escaping kostet vier Zeilen.

### B9 · `seen[code]` erbt vom Object-Prototype — Zeile 330 · **nice-to-have**

```
Bestätigungs-Code "constructor" → FALSCHE Warnung "kommt mehrfach vor"
```

Bei Airbnb-Codes (`HM…`) praktisch irrelevant, aber `Object.create(null)` ist

### B10 · Slash-Datumsformat wird immer als US gelesen — Zeile 280 · **nice-to-have**

`03/04/2026` → 4. März. Für den englischen Airbnb-Export richtig, für ein
DE-Locale-Resave falsch. Teilweise abgefangen: weicht die Nächtezahl von der

### B11 · `parseMoney` liest `1.234` als 1,234 — Zeile 283 · **nice-to-have**

Ein einzelner Trenner gilt immer als Dezimaltrenner. Bei `1.234` (deutsch: 1234 €)
ergibt das einen Faktor 1000. Airbnb schreibt Beträge immer mit zwei Nachkommastellen,
der Fall tritt praktisch nicht auf — die Heuristik „genau drei Ziffern nach dem
einzigen Trenner ⇒ Tausenderpunkt" wäre trotzdem sicherer.

## Antwort auf die Schlussfrage

**Ja — für Buchungen und Aufenthalte rund um den 01.07.2026 rechnet das Tool
korrekt.** Der Satzwechsel, die nächteweise Aufteilung, der Wegfall des
11 %-Pauschalabzugs und die Zuordnung zum Meldemonat entsprechen der Rechtslage,
und die exakten Tagesgrenzen sind verifiziert. Wer eine über den Stichtag laufende
Airbnb-Buchung auswertet, bekommt die richtigen Zahlen.

Die Einschränkung betrifft **Aufenthalte um die Drei-Monats-Grenze**: dort ist die
Fristberechnung bei Monatsend-Anreisen nachweislich falsch (B1), und die Befreiung
greift vermutlich zu weit (B2). Für den klassischen Kurzzeit-Vermieter ist beides
ohne Wirkung — für jeden Langzeitgast sollte die Zahl derzeit von Hand geprüft
werden, bis B2 mit der MA 6 geklärt ist.
